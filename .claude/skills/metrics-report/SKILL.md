# /metrics-report — 주간 마케팅 퍼널 리포트

## 목적
실유입 데이터로 **"이번 주 무엇을 할지 하나"**를 정하는 것. 숫자 나열이 목적이 아니다.

## 절대 규칙 (위반 시 작업 중단)
1. **실데이터만.** cta_events·waitlist 실제 행만 쓴다. 표본이 적으면 "적다"고 쓸 뿐, 추정·보정·예시 숫자를 섞지 않는다. (세션 #9 판정: 조작 데이터를 실측으로 위장하는 것은 불가)
2. **PII 금지.** waitlist 이메일 주소는 조회도 출력도 하지 않는다(스크립트가 select 하지 않음).
3. **쓰기 금지.** 이 스킬은 읽기 전용이다. 지표 테이블에 어떤 행도 삽입·수정하지 않는다.
4. 표본이 기준 미만이면 **판정하지 않는다.** "표본 부족"을 그대로 보고한다.

## 실행

```bash
# .env.local 의 값을 사용 (키를 화면에 출력하지 말 것)
set -a && . ./.env.local && set +a
SUPABASE_URL="$NEXT_PUBLIC_SUPABASE_URL" \
SUPABASE_SECRET_KEY="$SUPABASE_SECRET_KEY" \
REPORT_OUT="$TEMP/weekly-metrics.md" \
node .github/scripts/weekly-metrics.mjs
```

스크립트(`.github/scripts/weekly-metrics.mjs`)가 하는 일:
- 최근 7일(어제까지) vs 직전 7일, KST 경계. 오늘은 진행 중이라 제외
- 퍼널 3단계: 방문(VIEW) → 사전등록 클릭(CLICK_TRY) → 이메일 제출(WAITLIST_SUBMIT)
- 채널별(utm_source) 분해, `utm_source='test'` 제외, 빈 값은 "(직접)"
- 판정 기준선은 MARKETING-PLAN §1: **방문→제출 5%↑ 수요 신호 / 1%↓ 메시지 재점검**, 채널당 VIEW 30 미만은 보류

## 리포트 작성 (스크립트 출력 위에 얹는 부분)

스크립트 출력을 그대로 옮기지 말고, 아래를 **판단해서** 덧붙인다.

1. **한 줄 요약** — 지난주 대비 무슨 일이 있었는지 한 문장. 변화가 없으면 "변화 없음"이라고 쓴다.
2. **눈에 띄는 것 1~3개** — 채널 간 격차, 특정 단계에서의 이탈, 갑작스러운 증감. 없으면 없다고 쓴다.
3. **원인 후보** — 배포·SNS 게시·설문 배포 등 그 주에 실제로 한 일과 대조한다. `PROGRESS.md` 최신 세션과 `git log --since` 를 확인해 근거를 댄다. **추측은 추측이라고 명시.**
4. **이번 주 액션 1개** — 딱 하나만. 실행 가능하고 이번 주에 끝나는 것. MARKETING-PLAN Phase 0/1 항목과 연결한다.
5. **판정 보류 항목** — 표본 부족으로 아직 말할 수 없는 것을 명시. 언제쯤 판정 가능한지(필요 VIEW 수) 함께.

## 해석 시 주의
- **방문→클릭이 높은데 클릭→제출이 낮다** = 랜딩은 통했고 폼에서 막힌 것. `/preregister` 문제.
- **방문이 늘었는데 클릭이 안 늘었다** = 유입은 왔는데 메시지가 안 맞은 것. 채널-소재 정합 문제.
- **(직접) 비중이 크다** = utm 없이 들어온 유입. 링크 배포 시 utm 누락을 의심하고 USER_CHECK.md §2 링크 표를 점검한다.
- 사이트가 `/`(홈)·`/service`(서비스 상세) 2곳에서 VIEW 를 보낸다. 단 세션당 1회만 전송되므로 중복 집계는 아니다.

- 사용자가 "보기 좋게"·"공유"를 요청하면 Artifact 로 발행(artifact-design 스킬 먼저 로드).
- 정기 운영으로 남길 때는 GitHub Issue 생성을 제안하되, **발행·게시는 사용자 승인 후에** 한다.
